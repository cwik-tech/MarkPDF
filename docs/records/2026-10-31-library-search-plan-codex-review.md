# Independent review: library and exact-word search plan

**Verdict: changes required before implementation.** The overall architecture is workable, but option C currently has a path-provenance hole, and the upgrade can leave an older process using an unsafe forget implementation. Backfill, scope consistency, cancellation and several acceptance proofs also need corrections. An ADR is warranted for the consent, storage and public-contract choices.

Evidence boundary: source inspection and small SQL probes only; no install, build or test suite ran. Code-map inspection `A-cd4d2acfe20af310` completed through `heavy-run`; it detected Electron, but reported 110 files outside its configured roots, including core/CLI/MCP files, and unresolved imports. Its static findings are not behavioral verification; these boundaries were inspected directly. Probes used installed `better-sqlite3` 13.0.3 / SQLite 3.53.4 under Node 24.21.0. A separate Electron-as-Node probe confirmed Electron 39.8.10 / SQLite 3.53.4 / FTS5. The author's historical P1–P6 executions and performance numbers are **unverified independently**.

1. **Blocker — option C does not fail closed for app-recorded symlink paths.**

   **Evidence:** `docs/library-search-plan.md:364-366` says an alternative app path spelling fails the lexical check. That is false. `electron/main.ts:582-589` reads the requested path and returns its original spelling; `electron/semantic.ts:185-197` forwards it into indexing; `core/index/indexDocument.ts:269-272` persists it. `core/ipc/requests.ts:87-95` also permits bytes with a supplied, unverified path. `containsPath` assumes already-resolved paths (`core/consent/allowlist.ts:106-118`). In a temporary-directory probe, `granted/shortcut` was a symlink to a sibling private directory: `containsPath(granted, granted/shortcut/memo.pdf)` accepted it while its real target was outside the grant. This requires no malicious query.

   **Change:** Keep option C open, but require trusted canonical-path provenance recorded at ingestion. Existing rows with unknown provenance must be excluded from agent discovery until explicitly revalidated/reindexed; do not resolve paths during index-only search. Cover app path input, bytes-plus-path input, CLI ingestion, and an upsert of an existing hash that changes its recorded path (`core/store/index.ts:901-904`). Add a real symlink fixture and a mutation that bypasses the provenance requirement. Explain that C restricts *discovery*, not continued access to a known hash: single-document search/read still work after revocation. Explicitly disclose that the excluded-document count reveals inventory information.

2. **Blocker — migration neither excludes already-open old clients nor safely rechecks the version after locking.**

   **Evidence:** `docs/library-search-plan.md:436-437` incorrectly concludes that the triggers can never meet an old writer. `SchemaTooNewError` is checked only during open (`core/store/schema.ts:79-84`, `core/store/index.ts:462`). A probe kept a version-4 connection and prepared statements open, applied the plan's DDL from a second connection, closed that connection, then inserted and deleted through the old one. All operations succeeded. After the old checkpoint/VACUUM/checkpoint sequence, `oldwritersecretword` remained in the database bytes. Separately, `migrate` captures `from` before `run.immediate()` (`core/store/schema.ts:80-108`). Two connections that both observed version 4 reproduced `SQLITE_ERROR: table chunk_text_keys already exists` when the second applied the stale migration decision.

   **Change:** Specify an upgrade protocol that establishes exclusive access before installing version 5, refuses safely while an old connection is attached, and re-reads the schema version under the acquired lock before DDL. Merely adding `IF NOT EXISTS` does not establish the protocol. Document the close/restart remedy. Add coordinated real-process tests for simultaneous upgrade attempts and a pre-existing version-4 connection; mutation-prove both the exclusivity requirement and the locked version recheck.

3. **Major — “one document per batch” does not bound backfill work or guarantee responsive cancellation.**

   **Evidence:** `docs/library-search-plan.md:456-474` makes a whole document one synchronous write transaction, while `:637` requires no transaction over one second. There is no maximum document chunk count. `completeExactIndex` specifies abort checks but no event-loop yield. With synchronous SQLite, releasing a lock or awaiting an already-resolved promise does not let IPC cancellation, progress delivery or quit run. Existing indexing explicitly injects `setImmediate` for this reason (`electron/semantic.ts:209-211`). The final missing-key step at plan `:459-461` is also ambiguous: it describes finding and adding one missing chunk, then declaring completion.

   **Change:** Bound each transaction by chunk count and/or text bytes, persist a stable document/chunk cursor atomically with its inserted rows, and yield through an injected event-loop callback between batches. Define completion as an empty anti-join checked in the same write transaction as the completion marker; repair *all* gaps through bounded batches. Specify behavior when another worker has already completed or clear resets the marker. Register every app backfill entry path, including search-triggered work, with the drain mechanism. Test one oversized document, multiple holes below the cursor, cancellation received from the actual event loop, clear/quit, rollback and process restart.

4. **Major — the update trigger creates unmapped FTS rows before backfill.**

   **Evidence:** The DDL at `docs/library-search-plan.md:414-419` assumes the key exists. A probe executed that DDL with a legacy chunk lacking a key, updated its text, then deleted the chunk and ran `optimize`. The update inserted an automatically allocated FTS rowid without creating a key. `fts5vocab` still contained `orphansecretword` after deletion and optimization. The final backfill check only detects chunks without keys; it cannot detect this orphan. No current production path updates chunk text, so present-day reachability is limited, but the plan explicitly promises this trigger protects future updates (`:431-432`).

   **Change:** Either make chunks explicitly immutable and reject unsupported updates, or ensure the update transaction creates/uses a stable mapping before inserting FTS content. Define whether chunk identifiers may change and reject or handle that case too. Add update-before-backfill, update-after-backfill, rollback, delete-after-update and mapping-integrity cases. Mutation-prove the missing-key case. Do not leave a speculative trigger whose claimed safety is false.

5. **Major — forget has an unhandled delete-to-optimize crash/failure window.**

   **Evidence:** The plan puts `optimize` after `removeDocument.immediate()` (`docs/library-search-plan.md:486-488`); deletion is already committed. Existing `forgetDocument` returns immediately when the document no longer exists (`core/store/index.ts:1057-1062`). A crash or optimization failure therefore leaves token tombstones and no document on which a retry will run cleanup. The crash table at plan `:778-789` omits this window. Independent probes corroborated the need for optimization: single-transaction, separate-transaction and already-optimized layouts retained the unique token after delete/VACUUM and removed it after optimize/VACUUM.

   **Change:** Specify recoverable erase state, written atomically with logical deletion, and resume pending cleanup under exclusivity before claiming success, including when the document row is already absent. Define the outcome for optimize, checkpoint and VACUUM failure. Add fault/restart tests at each durable boundary and inspect database plus WAL before close. Retain the existing refusal-before-deletion test. `optimize` before VACUUM is a sound direction, but successful raw-SQL examples do not establish recovery. SQLite documents the contentless-delete tombstones and their removal during merging: [FTS5 deletion and merging](https://www.sqlite.org/fts5.html#the_deletemerge_configuration_option).

6. **Major — the exact SQL does not implement the declared active scope.**

   **Evidence:** `docs/library-search-plan.md:538-540` includes model id, model version and dimensions in eligibility. Its SQL at `:556-566` filters only document, chunking profile and chunking version. The current search includes all six scope fields (`core/store/index.ts:983-989`), and chunk identifiers deliberately omit model identity (`core/index/chunkIdentity.ts:42-55`). Selecting a document because it has one active-model chunk does not make every chunk in it belong to that model scope. Exact hits can consequently fall outside the semantic scope whose timestamp is reported.

   **Change:** Choose explicitly: either exact search is model-independent, with mode-specific eligibility/counts/provenance, or exact SQL must use an `EXISTS` predicate for the complete embedding scope per chunk. Keep timestamp lookup consistent with that choice. Test mixed models, versions, dimensions and partial indexing within the same document; mutate each relevant scope restriction. Preserve the correct latest-row-per-path rule and distinct pathless rows, applying that selection before grants/scope so an excluded new version does not resurrect an older version.

7. **Major — multi-stage library reads need one database snapshot.**

   **Evidence:** The plan separates document selection, semantic candidate collection, text retrieval, exact ranking and per-hit `chunksWrittenAt` reads (`docs/library-search-plan.md:304-307`, `:532-566`). It specifies no read transaction. Another process can replace chunks between these reads, leaving missing candidates, rankings from different states, or a completion timestamp that did not describe the ranked content. The repository already explains and prevents this class of mixed-state read in `readReusableIndex` (`core/store/index.ts:813-823`).

   **Change:** Compute the embedding outside the database transaction, then take a short consistent read snapshot for eligibility, both rankings, selected-hit materialization and provenance. Specify how cancellation and long scans release it. Add a coordinated writer/read interleaving test and mutation that removes the snapshot boundary. Do not treat `indexSnapshot: true` alone as a consistency mechanism; it currently distinguishes index content from current file bytes.

8. **Major — quoting blocks operators but does not make every MATCH input safe.**

   **Evidence:** Following `docs/library-search-plan.md:511-516`, the word `abc\u0000def` becomes a quoted FTS string containing NUL. The installed SQLite returned `SQLITE_ERROR: unterminated string` for that bound parameter. Ordinary quoted `text:secret` and doubled unmatched quotes did not escape into query syntax in probes. MCP already rejects control characters (`mcp/arguments.ts:30-35`), but the core/IPC text guard only requires a nonempty string (`core/ipc/requests.ts:29-33`), so the builder cannot rely on the MCP guard for all surfaces. The proposed “tokenizer would turn into nothing” test is not defined precisely enough to implement.

   **Change:** Specify typed validation for NUL at the shared boundary, finite input/part limits, and the actual Unicode61-compatible token-presence rule, including private-use characters and combining marks. Continue binding the resulting expression as a parameter. Exercise generated expressions against real FTS5, not only expected expression strings: NUL, embedded/doubled/unmatched quotes, operator spellings, punctuation-only input, Unicode and oversized input. Exact should reject invalid/no-token queries predictably; hybrid's semantic fallback must be deliberate. Also prove exact mode does not embed or download a query model.

9. **Major — candidate depth followed by a document cap can hide the rest of the library.**

   **Evidence:** At default `topK = 12` (`core/models.ts:122`), the plan fetches 50 candidates per ranking, then keeps at most three per document (`docs/library-search-plan.md:575-582`). If both top-50 lists belong to document A, the reply contains only three hits even when B through Z have qualifying hits immediately below that cutoff. This defeats the intended diversity and has no disclosed exhaustion indicator. Exact SQL also orders only by BM25 (`:565`), so equal scores can change rank positions before the RRF tie-breaker ever applies.

   **Change:** Specify diversity-aware candidate retrieval or bounded adaptive expansion until enough distinct-document hits are available or the search budget is exhausted. Disclose deliberate candidate truncation separately from output-byte truncation. Define stable ties in each input ranking, such as chunk id, before assigning RRF positions. Add a dominant-document fixture, ties across batches/reopen, and candidate-depth sensitivity measurements. The RRF formula and score direction themselves are coherent.

10. **Major — the app contract omits promised mode selection and leaves search-state ownership unspecified.**

    **Evidence:** The plan lists three modes on every surface (`docs/library-search-plan.md:162`) but hardcodes app Library to hybrid and This document to semantic (`:314-328`). The text-layer find bar is not the new FTS/BM25 mode. Existing `applySearch` gates semantic work on the active tab being ready and uses one request id (`src/App.tsx:2582-2603`); the panel gates results on that tab's index status (`:5315-5322`). The plan does not say how Library bypasses those document-specific gates or invalidates an in-flight request when scope/model/tab changes.

    **Change:** Add an explicit mode control for the promised app search capability, or obtain an explicit scope reduction. Define ownership of library query/results/loading/error state; allow searching the existing library when the active PDF is unindexed. Specify stale-response rejection on query, scope, model/profile and tab changes, plus pending-target cleanup when opening fails. Keep the start-screen placement question open as already planned. Add real Electron journeys for mode selection, switching to an already-open hit, a missing/pathless hit, and a scope/tab switch while a result is pending.

11. **Major — the plan narrows the required output-bound contract without approval.**

    **Evidence:** `docs/library-search-plan.md:605-610` applies `budget.ts` only to library JSON and explicitly leaves the changed single-document command path unbounded by it. Library human output is not covered. The app exemption at `:329-332` also claims `topK` plus snippets bound the reply, but headings and names remain variable-size (`core/index/search.ts:13-21`, `core/store/index.ts:997-1004`). `boundItems` and `fitReply` exist to cover precisely these two different costs (`core/output/budget.ts:315-349`, `:100-139`). Requirement 6 does not grant the stated exemption for the command's single-document results.

    **Change:** Route changed CLI/MCP search responses through the shared content and serialized-reply budgets, including new fields and document metadata. Define the human-output limit and render from the bounded hit set. For IPC, either apply explicit metadata bounds or document a deliberately narrower approved contract; do not claim a total reply bound from snippets alone. Test actual serialized transport text and omissions, including long headings/names/paths, escaping, an oversized first hit and an empty result. Ensure formatting after fitting does not invalidate the promised byte unit.

12. **Major — mode, score units and explicit min-score need a complete adapter contract.**

    **Evidence:** The plan changes `score` between cosine, negative BM25 and RRF (`docs/library-search-plan.md:588-595`), but only its library examples carry `mode`; the single-document shape is otherwise retained (`:254-255`). A hybrid result with only semantic candidates is indistinguishable by `matchedBy` from semantic mode. The command-table description still promises “Discard passages scoring below this” (`cli/spec.ts:144`), which is false for hybrid exact-only hits. Both current adapters replace absent min-score with settings before calling core (`cli/commands/searchCommand.ts:108-110`, `mcp/operations.ts:292-294`), losing the explicit/implicit distinction required by plan `:214-216` and `:268-269`.

    **Change:** Return the selected mode in both single-document and library responses, update the command-table description inherited by MCP, and preserve the raw optional min-score until the shared mode rule has validated it. Apply the settings fallback only to semantic/hybrid execution. Include the new fields in the MCP result mapper (`mcp/operations.ts:305-316`), which currently selects fields explicitly. Keep the default open question and prefer retaining semantic for existing single-document callers unless the user accepts the score/threshold compatibility change. Add explicit-versus-absent threshold cases and a hybrid exact-only result below the semantic threshold.

13. **Major — the proposed acceptance/mutation tests leave several high-risk rules unproved.**

    **Evidence:** The first CLI journey is an appropriate thin real-stack boundary, and core store tests are the right layer for SQL persistence. However, “two passages” at `docs/library-search-plan.md:672-678` does not ensure two distinct chunks; place them on separate known pages. Capability 4 expects the exact hit first (`:707-709`) while the contract retains page ordering (`:583-584`), so a semantic distractor on an earlier page can legitimately come first. The no-filesystem mutation removes a no-path check (`:767`), which does not test absence of filesystem calls. The combined CLI grant journey is the only named grant mutation proof (`:766`); MCP's outer test covers only granted documents. Two synchronous connections exercised serially are not a contention proof, as the existing test commentary acknowledges (`core/store/store.test.ts:374-378`).

    **Change:** State Red-first and post-refactor Green explicitly for every capability, including expected behavioral failures after any initial unknown-option/missing-interface failure, as required by `AGENTS.md:104-119` and `:139-145`. Make the hybrid acceptance select `top_k: 1` with a fixture where exact rank changes membership, or assert the documented page-order contract separately. Use a missing-on-disk stored path to mutation-test replacing the lexical predicate with a filesystem-resolving predicate. Add MCP revoked/never-granted/pathless cases in the same long-lived session. Add controlled real-process lock interleavings, atomic key/FTS/cursor rollback, clear/drain and cancel-no-output proofs, surviving-document exact hits after forget/VACUUM and FTS rowid reuse, and visible Electron wrong-tab/stale-result mutations. Put exact-query execution tests beside the pure builder tests. Keep unrelated rule matrices out of the outer journeys.

14. **Major — the proposed performance fallback can serve stale or forgotten data.**

    **Evidence:** `docs/library-search-plan.md:656-657` proposes a per-process cache keyed by scope and checked only with `PRAGMA data_version`. That pragma does not change for commits on the same connection. A two-connection probe read version 2, inserted through the same connection, then read version 2 again. The app indexes and forgets through its existing store handle (`electron/semantic.ts:194`, `:274`, `:285`), so this invalidation rule misses precisely those local writes. See [SQLite data_version semantics](https://www.sqlite.org/pragma.html#pragma_data_version).

    **Change:** Keep caching out of the initial implementation unless measurement requires it. If introduced, require local write-generation invalidation as well as same-connection comparisons of `data_version` for external commits, scope/candidate isolation, and eviction on forget/clear. Mutation-prove local and external reindexing, forget and clear. Extend the benchmark to measure maximum transaction duration, peak resident memory, event-loop delay/cancellation latency and concurrent-process busy outcomes, using skewed document sizes and rare/common/multiword/no-hit queries. Fix the delivery dependency: a benchmark of production library search cannot run before that implementation exists (`docs/library-search-plan.md:640-651`, `:840-841`); separate an early store probe from the later end-to-end measurement. Warm search targets excluding embedding are useful subsystem targets, not an app responsiveness guarantee.

15. **Minor — correct the unsupported citation claims and constrain the ADR work.**

    **Evidence:** Most file/line references point to the claimed code: the version-4 schema, write/delete paths, latest-path ordering, full cosine, page ordering, consent lookup, command limits, MCP schema generation and budget constants are correctly located. The materially wrong implications are the fail-closed app spelling claim and old-writer exclusion addressed in findings 1 and 2. `docs/library-search-plan.md:799-800` also incorrectly says the retrieval skill searches only by hash: `skills/markpdf-retrieval/SKILL.md:19` explicitly searches an open document by ref. “Nobody has measured” at plan `:49`, population claims about how many app documents lack grants, and “DDL runs in milliseconds” at `:438` are not established by their cited code or retained probe evidence. Mark them **unverified** or narrow them to what was inspected/measured.

    **Change:** Correct those statements and preserve reproducible probe source/fixtures/environment alongside any measurements that will justify decisions. Retain the integer key table: SQLite explicitly warns that VACUUM may change rowids without an INTEGER PRIMARY KEY ([VACUUM documentation](https://www.sqlite.org/lang_vacuum.html)); observing no change in P6 is not a guarantee. Independent probes also confirmed insert/delete within a transaction, rowid reuse, trigger rollback and the planned clear ordering, so these do not need redesign on speculative grounds. The separate `search_library` tool is defensible and preserves explicit intent; deriving its valued options from `cli/spec.ts` avoids the boolean-schema limitation. Write a short new ADR for the hard-to-reverse consent/storage/interface choices, linking the detailed design and verification matrix. Clarify that “amends” at plan `:374-375` and `:793-797` means a new superseding decision and, if necessary, only a status-line change to an accepted ADR, not editing its accepted decision text.
