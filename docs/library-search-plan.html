Baseline · the code at 2125a71, before this work

At the base commit, a search reaches one document, by meaning only

markpdf search needs exactly one of --path or --id. The store compares the query vector with every stored passage of that one document. None of the seven MCP tools does an exact-text search. The app's Semantic Search pane runs only for a ready, active PDF tab.

The plan confirms the claims of the idea brief, with one exception. Before this work, no measurement record existed in docs/records/, and whether anyone measured library-scale cost elsewhere is unverified. The measurement record now exists. Five facts that the brief did not mention change the design.

  1. FTS5 can keep a forgotten document's words in the file. Probes P2 to P4 and the Codex probes show it. See Forget.
  2. document_chunks has a TEXT primary key. SQLite documents that VACUUM can change rowids of such a table. The plan gives each chunk its own integer key. See Upgrade.
  3. One file path can have more than one documents row. A changed file that was indexed again keeps its old row. Library search takes the latest row for each path. See Ranking.
  4. The app records the path that the renderer sends, without resolving links. A bytes request can also carry a path that nothing checked. See Consent.
  5. The upsert overwrites file_path on every write of a known hash. A document that the command indexed can later carry a path that the app recorded. See Consent.

Library state in the app

Library state belongs to the app, not to a tab. It holds the query, mode, results, loading state, error and its own request id. A Library search works when the active PDF is not indexed. The app drops a response when the query, scope, mode or settings changed after its request.

A click uses the pure rule libraryHitTarget(tabs, hit). If a tab has the same content hash, the app switches to it and sets the page and highlight. Otherwise, if the hit has a path, the app opens it with a pending page and highlight. A failed open clears the pending target and shows a message. Discovery in a library search · changes

The command and MCP keep only rows with path_provenance = 'resolved' inside a current read root. The check is lexical through containsPath. It makes no filesystem call and never calls isAllowed or requireAccess. The reply counts the other documents in documentsNotDiscoverable, without names or paths.

Access to a known document · unchanged

A single-document search and read_pages by hash still work after a grant is removed, as the consent ADR records. The journey test at cli/journeys/consent.test.ts:63 stays green. MCP has no option that widens the rule.

How provenance is written

  • The value resolved means that the writer resolved the path through requireAccess and read the bytes from that resolved path. Any other writer stores NULL.
  • The command's index run writes resolved. The app and every bytes request write NULL.
  • The value is written with file_path on every upsert. So a later app write of the same document removes it.
  • Rows written before version 5 have NULL. A person makes them discoverable again with markpdf index <folder> --recursive, which reuses the index and records the provenance.
  • The count in documentsNotDiscoverable shows how many other documents the index holds. The plan accepts this, because the count explains an empty answer and the command prints the remedy on stderr.

Safety rule 1 · forget and clear

Forget and clear merge the full-text index, and an erase flag survives a crash

Forget withdraws consent for indexed content. Today it runs secure_delete, a checked checkpoint, VACUUM and a second checkpoint under exclusive access. Deleted FTS5 rows can leave their words in segment records. secure-delete and VACUUM alone did not remove them. FTS5 optimize did.

ProbeLayoutWithout optimizeWith optimize
P250 chunks per document, three transactionsThe token stayed after delete and VACUUM, with or without secure-deleteRemoved
P3200 chunks per document, one transactionsecure-delete alone removed itRemoved
P450 chunks per document, one or three transactionssecure-delete alone left itRemoved

The erase rule

  1. removeDocument and wipe set exact_index_erase_pending in their own transaction.
  2. forgetDocument takes exclusive access and removes the document, if it exists.
  3. If the erase flag is set, it runs optimize, then the existing reclaimSpace.
  4. It clears the flag and runs one more checked checkpoint.

A crash or a failure after the delete leaves the flag set. The next forget or clear finishes the erase before it reports success, also for a document that no longer exists. clear runs delete-all on the FTS table, then the same steps. The existing refusal before deletion stays.

At 100,000 chunks a separate probe measured optimize at 1,065 ms and VACUUM at 2,964 ms on a 436 MB file. That probe used vectors in the chunk row and about 2,500 generated words, so its file is larger than the scale probe's store.

Question 3 · schema change and in-place upgrade · safety rule 2

Schema version 5 installs only when no other connection is attached

The store is at schema version 4 today. Its migration reads the version before it takes the write lock, so two processes that both read version 4 can both try the same DDL. A process that opened the file before an upgrade keeps its old code. Codex reproduced both faults. An old process that stayed open kept writing after the upgrade, and its forget left words in the file.

  • documents.path_provenance is a new column for the consent rule.
  • chunk_text_keys gives each chunk a stable INTEGER PRIMARY KEY, because VACUUM can renumber an implicit rowid.
  • chunk_text_fts is a contentless FTS5 table with the unicode61 remove_diacritics 2 tokenizer.
  • An insert trigger and a delete trigger on document_chunks keep the index equal to the table. The delete trigger owns the key row.
  • The trigger document_chunks_immutable refuses an update of id or text. An update would need a key that a legacy row does not have yet. No code updates a chunk row today.
  • schema_meta gets three keys: exact_index_state, exact_index_cursor and exact_index_erase_pending.
1 · Version under the lockRead the version inside the write transaction. A process that finds the work done does nothing. This also fixes the same race for versions 1 to 4.
2 · Exclusive accessFor an existing file below version 5, take exclusive access first. If another connection is attached, refuse with StoreUpgradeBusyError and change nothing.
3 · InstallInstall the version 5 DDL and stamp the version in the same transaction.

A brand-new file at version 0 needs no exclusive access, because no older process can have it open. The busy refusal says: "MarkPDF must upgrade its index, but another MarkPDF window, command or agent session has it open. Close them and try again." The command maps it to exit 9, index busy.

The DDL does not tokenize existing text. Its duration was not measured on its own. The backfill, which does the tokenizing, is in the measurement record.

Question 3 · backfill of documents that are already indexed

A backfill fills the index in bounded batches of 500 chunks and yields between them

Existing chunks have no key row and no index entry after the upgrade. The backfill adds them. Each batch is one IMMEDIATE transaction, together with its cursor.

1 · CursorRead the cursor, a pair of document_id and chunk id.
2 · BatchRead the next 500 chunk rows in that order. Add a key row and an index row for each row without a key. Move the cursor.
3 · End checkAt the end, look for any chunk without a key in the same transaction. If none, write complete. If one exists, reset the cursor.
4 · YieldBetween batches, completeExactIndex checks the signal and awaits yieldControl.

After a cursor reset, the next batches repair all gaps in the same bounded way. When the state is already complete, a batch does nothing. Clear sets complete.

Who runs it

  • The app's main process starts one shared job after the store opens. The job registry holds it, so a clear drains it and quit cancels it. A library search awaits the same job.
  • The command and MCP run it before an exact or hybrid search when the state is not complete. The command shows progress on stderr. MCP sends progress notifications when the client gave a token.
  • Two processes can run batches at the same time, because each one reads the cursor inside its write transaction.

Clear drains jobs: core/index/clearIndex.ts:13-17. MCP progress: mcp/operations.ts:40-41. Yield pattern today: electron/semantic.ts:209-211.

Exact query handling

A raw query never reaches FTS5, and control characters are refused

buildExactMatch(query) in core/index/exactQuery.ts returns an expression or a refusal. It refuses a control character, including NUL, because Codex showed that NUL makes FTS5 fail even inside quotes. It refuses a query longer than 1,000 characters or with more than 32 parts.

It splits the query into quoted phrases and bare words, and drops each part that has no token character. It puts each part in double quotes, doubles each inner quote, and joins the parts with spaces, which FTS5 reads as AND. The result is bound as a parameter.

InputExpression
clause 4.2(b)"clause" "4.2(b)"

NEAR(a b)"NEAR(a" "b)"

abc\u0000defRefused

In this plan, "exact" means exact words. The tokenizer folds case and removes diacritics, and a phrase matches consecutive tokens. So "clause 4.2(b)" also matches "Clause 4-2 b".

Question 4 · ranking and modes

Hybrid mode fuses the two rankings by position, inside one read snapshot

The command takes --mode, and both MCP tools take mode. The default for these three is hybrid. The app always sends a mode. Every reply states its mode, so a caller can see the meaning of score.

All reads of one library search run in one deferred read transaction: candidate documents, both rankings, the text of the selected hits, and chunksWrittenAt. The query embedding runs before it. So a writer between the stages cannot mix two states of the index.

RRF scores each chunk with fused(c) = Σ 1 / (60 + rank(c)), with rank from 1. It uses rank positions only, so bm25 and cosine need no common scale. Ties go first to a chunk in both rankings, then to the higher cosine, then to the chunk id. The adapters pass the raw optional --min-score, and core decides.

Which documents a library search ranks

  1. For each recorded path, the row with the latest last_opened_at, then the highest id. Each row without a path counts on its own. This runs first, so a newer version that a later step excludes cannot bring back an older one.
  2. On the command and MCP, rows with path_provenance = 'resolved' inside a current read root.
  3. Chunks with the active profile and version, and an embedding with the active model, model version and dimensions. The exact ranking applies this through EXISTS on chunk_embeddings. A document with no eligible chunk counts in documentsOutsideActiveScope.

Depth, cap and truncation

Each ranking starts with a depth of min(400, max(50, 4 × topK)). A library list keeps at most libraryHitsPerDocument = 3 passages from one document, then cuts to topK. If the list is shorter than topK and a ranking filled its depth, the depth doubles and the search ranks again, up to 1,600. If a ranking still fills 1,600, the reply says candidatesTruncated: true. A library list stays in rank order. A single-document search has no cap and keeps page order.

Question 5 · output bounds

A new core function, boundSearchReply in core/output/searchReply.ts, takes the hits, the fixed fields and a render function. It bounds the reply in two steps.

2 · Content boundboundItems keeps whole hits within DEFAULT_CONTENT_BUDGET, 20,000 bytes of document text.
3 · Reply boundfitReply fits the finished JSON into DEFAULT_REPLY_BUDGET, 48,000 bytes.

Left out on purpose

What this plan does not build

  • A vector extension such as sqlite-vec, which is a new package, and any per-process vector cache.
  • Substring search with the trigram tokenizer.
  • A query language beyond words and quoted phrases.
  • A forget command or MCP tool.
  • A library search box on the app's start screen.
  • Exact or hybrid modes in the app's per-document panel. It stays semantic, because the find bar covers exact words in the open document.
Question 7 · the TDD policy

Each capability starts Red at its outer test, and each kind of rule has its own test layer

This work is a new cross-layer user capability. So each vertical capability starts with an outer acceptance test that runs Red first. Inner loops drive the rules, and each capability ends Green after refactor. When a first Red is only a missing option or export, the implementer adds the minimum interface and runs the test again to reach a behavioral failure.

The table gives the layer for each kind of rule. Rule matrices, such as the stale-response and hit-target rules, are pure tests. The live quality test with the real model is deferred and not written.

The first fixture puts "clause 4.2(b)" and "clause 2.4(b)" on separate pages. The test embedder is a bag of words, so only the phrase match separates the two pages.

Exception to the TDD order

Two pieces of code came before their tests

The upgrade protocol was written in the schema step of capability 1. The hybrid branch of the fusion was written in the semantic step of capability 1. For both, the mutation that removes the rule is the Red evidence. The protocol tests and core/index/fusion.test.ts fail under the mutation and pass when the code is restored.

Defects and design problems that the tests found

  • The existing forget sequence left the exact-word tokens of a forgotten document in the file.
  • The first Electron journey asserted too early to see a highlight being cleared.
  • Two older migration tests write a version 2 file without schema_meta. The version 5 step now creates that table when it is missing.
  • The core boundary test forbids the identifier document, which the first library code used.
  • A library test indexed documents without their cached text. So their scope was never claimed, and snapshotRecordedAt was null. The fixture now stores the text, as real indexing does.

Existing tests that changed

  • cli/commands.test.ts and mcp/operations.test.ts: the threshold-source tests now pass mode: semantic. Under the new hybrid default, the threshold does not filter an exact match. This is the intended contract change.
  • cli/help.test.ts: the synopsis now lists --library.
  • mcp/toolSchemas.test.ts and mcp/journeys/toolSession.test.ts: eight tools.

Deviations from the plan

  • The opt-in retrieval quality test with the real model is not written.
  • The Electron journey covers the main outcome. Switching to an open tab, a missing file and a pathless hit are covered by src/libraryHitTarget.test.ts, not by separate journeys.
  • migrateFrom is exported, so that a test can pass a stale observation of the version.
  • If two new MarkPDF processes open an older index at the same moment, both can refuse the upgrade. Opening again succeeds. The ADR records this.

Question 8 · ADR · recorded

Yes, the work needs an ADR, and the earlier ADRs keep their decision text

The new ADR is docs/adr/2026-10-31-Library-And-Exact-Word-Search.md. The work needs one for four reasons. It changes the store schema. It adds a derived index that consent withdrawal must erase. It changes a consent consequence of an earlier ADR. It adds an MCP tool to a list that an earlier ADR keeps small.

  • It records the consent rule with provenance, the FTS5 design, the upgrade protocol, the erase rule, the ranking and the eighth MCP tool.
  • Its Verification section names the tests of the test plan.
  • It states which consequences of the consent ADR and the MCP server ADR it supersedes. It does not edit their decision text.

The other documents are delivered. The README has the command usage, --library, --mode, and the MCP table with eight tools. The markpdf-retrieval skill has the library route and the exact mode, next to its search by hash and by open-document ref. CHANGELOG.md has three entries under Added and two under Fixed. Evidence and limits

The tests, the build, the Electron journeys and the benchmark ran

The plan cites file:line at 2125a71 for each claim about existing behavior. Its six early probes ran raw SQL that imitates the store, and they did not run the production code path. The probe sources are not kept in the repository. The implementation record gives the test runs, and the measurement record gives the benchmark.

Checked
  • The claims of the idea brief, against the code.
  • P1: FTS5, secure-delete, contentless_delete and trigram are available in SQLite 3.53.4 with better-sqlite3 13.0.3, under Electron 39.8.10 and Node 24.21.0.
  • P2 to P4: optimize removed the deleted token in every layout.
  • P5: query and backfill times at 20,000 and 100,000 chunks, and the cost of forget.
  • Codex probes: the symlink path, an open version 4 connection, the update trigger and NUL in a query. Each one disproved an assumption, and the plan changed.
  • The Codex review, with a decision for each of its 15 findings.
  • The six outer tests, Red first and then Green, and 18 mutation runs.
  • The final runs on 1 November 2026: six typechecks clean, 128 files and 1,538 tests passed, the build passed, and 37 Electron journeys passed.
  • The benchmark at 10,000, 100,000 and 500,000 chunks, with the result in the measurement record.
Not established
  • A mutation proof for the clear erase. The mutation did not bite.
  • Retrieval quality with the real model. The test is not written.
  • App responsiveness. The performance targets are store-level only.
  • Rowid stability through VACUUM. P6 saw no change, but SQLite does not guarantee it.
  • The two follow-ups: the start-screen search box, and the action for the failed targets.
  • Lint. The repository has no lint command.
