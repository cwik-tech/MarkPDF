MarkPDF · agent evidence and agent comments · 31 October 2026 · plan, review and implementation record

Agents will point to evidence and propose comments. Only the person can put a proposal in the file.

This plan adds two features to MarkPDF that share one route from an agent to the running window. With reveal, an agent brings a document to the front and marks the passage that it cites for a few seconds. With agent comments, an agent reads every comment as data and proposes new ones in a separate suggested layer. A proposal reaches the file only when the person accepts it and then saves. Codex reviewed the plan, and the plan accepted all 13 findings. The plan is now implemented in this worktree and not committed.

Scope

Three new tools for PDF documents, and the link on macOS only

The plan adds the commands reveal, comments and suggest, and the MCP tools reveal, read_comments and suggest_annotation. It also changes the app UI, the IPC contract, the command table, the output bounds, the docs and the retrieval skill, and it adds two ADRs.

Scope decisions · 31 October 2026

Both features are planned together, and cli/spec.ts stays the single source for MCP schemas

The two features share one route from an agent to the window. The new MCP tools take every property from their cli/spec.ts entries with propertyFromOption. They do not repeat the hand-written ref of search and read_open_document.

What the command table gets

  • String options get an optional maxLength. The MCP schema publishes it, and both the MCP validator and the command-line parser enforce it.
  • All three commands take exactlyOneOf: ["path", "id", "ref"] and have no default identity (finding R7). Today the validator fills defaults before it checks oneOf.
  • A generator in mcp/toolSchemas.ts derives a three-branch oneOf from exactlyOneOf. Each branch has not clauses for the other two identities.
  • A new flag agentFacing: true makes the parser refuse grant flags for these commands (finding R6).
  • The tool count goes from seven to ten. The stdio journey that lists exactly seven tools changes with it.

Left out on purpose

  • Markdown tabs. The three tools accept PDF documents only in this iteration.
  • Reply threads. read_comments reports the /IRT link as data, and the UI does not change.
  • Edits or deletion of an existing comment by an agent. An agent can only propose.
  • A new author name for annotations by people. It stays MarkPDF.
  • A change to the existing preparation protocol. The new channel is separate (finding R4).
  • URL scheme registration on Windows and Linux.
  • More than one suggestion in one call. MCP arguments cannot be arrays today, so batching is deferred.
  • The uncommitted Mermaid viewer work in the main checkout. This plan does not depend on it.

Question 1 · how a request reaches the running app

Each request names one concrete target and travels through a private file channel

The client is core/agent/desktopChannel.ts. It writes a request file and starts the Electron binary with --markpdf-request=<id>. The single-instance lock forwards that argument to the running app. If no app runs, the new process becomes the app.

The right column names the Codex finding behind the rule of each step.

  1. The agent calls reveal or suggest_annotationThe server validates the arguments, resolves ref "active" to one concrete tab or path, and checks the read grant.R5
  2. The client writes <id>.request.jsonMode 0600, flag wx, with its own deadline, in session/desktop-requests/.R4
  3. The client starts the Electron binaryThe single-instance lock forwards --markpdf-request=<id> to the running app.new
  4. The desktop consumes the request once and checks the grant againIt validates the request, checks the grant, revalidates the tab, then writes <id>.ack.R4
  5. Main sends agent:reveal or agent:suggest to the owning windowThe window checks the tab and its revision, anchors the quote, and shows the mark or adds the suggestion.R3
  6. The window answers with agent:revealed or agent:suggestedMain accepts the answer only from the window that owns the request.new
  7. Main writes <id>.result.jsonExclusive temporary file and rename. The client checks the id and the size, and the agent gets a bounded reply.R4

Target binding (finding R5)

  • There is no default identity. The caller names exactly one of path, id or ref. --ref active names the document at the front.
  • The client resolves ref: "active" once into a concrete reference. A stale reference fails at once, and no process starts.
  • An id becomes the path that the index records.
  • The desktop accepts a reference only when its process part is the desktop's own process.pid. Just before the IPC message, it checks again that the window and the tab still exist.
  • If a path or an id matches more than one open tab, the desktop refuses with ambiguous. The remedy is "Name the tab with a ref from list_open_documents."
  • The window answers document_changed when the tab is gone, or when its document revision changed while the quote was matched.

Timing

  • If no acknowledgement arrives within 5 seconds, the client answers "MarkPDF did not answer. An older MarkPDF can be running. Restart MarkPDF and try again." An old app treats the unknown argument as "focus the window".
  • The deadline is 30 seconds for reveal and suggest, including a cold start. The desktop refuses an expired request before it changes anything in a window.
  • At most 4 desktop requests run at a time. Another request receives busy.
  • read_comments does not use this route. It reads the saved file in core.
Risk · measured in the implementation

Each request starts the Electron binary only to forward its argument

The plan did not measure the start time to the single-instance lock. Capability 1 measures the time from the call to the reply with a warm app. If the median is above 1.5 seconds, the follow-up is a directory watcher in the running app.

The implementation record gives a warm call-to-reply time of 258 ms for the first reveal journey.

Question 1 · the request files

The new requests use a separate, hardened channel, and the preparation code does not change

Codex found four limits in the preparation channel (finding R4). The preparation ADR chose a file channel over a socket, and this plan keeps that kind of channel. It builds the new requests on a separate channel with strict file rules.

Preparation channel today · unchanged

Four limits that Codex found

  • The desktop calls stat and readFile separately.
  • The temporary result name is predictable and not created exclusively.
  • The client reads the result without a size limit.
  • Abandoned files stay.
agentPreparation.ts:92-94, 85-88 · desktopClient.ts:30, 22-27
New request channel · planned

File rules for the new channel

  • The desktop opens a request with O_NOFOLLOW, checks it with fstat on the opened descriptor, and reads at most 16 KiB.
  • The result goes to a temporary file with a random name and flag wx, then a rename.
  • The client reads the result through a descriptor with the same 16 KiB limit and fstat check.
  • On start, the desktop removes matching files that are older than one hour.
Plan section A2, file lifecycle.

Other file rules

  • A request id is a UUID that matches one strict pattern. The desktop builds every path from the fixed directory and that id, and refuses any other name.
  • The desktop creates the directory with mode 0700. It refuses the directory when it is a symbolic link or belongs to another user.
  • The desktop consumes a request once. It renames the request to <id>.taken before it parses it, so a second delivery finds nothing.
  • A bounded in-memory set of recent ids blocks a replay in the same run.
  • The result carries the request id, and the client refuses a result with another id. Then the client removes the request, acknowledgement and result files.
Threat model

The files do not authenticate the agent

Any process of the same user can write a request, read the signing key and start the binary. The file rules protect against other users and against malformed or replayed input. The grant checks protect the person's files.

Question 2 · security of the markpdf:// link

Only a link that this MarkPDF signed can reveal a passage

The operating system can deliver a markpdf:// address from any application, for example a web page, an email or a PDF in another reader. MarkPDF cannot stop that delivery. Thus the plan signs every link that MarkPDF makes, and every other link is inert.

The link format

markpdf://reveal?v=1&doc=<64 hex content hash>&page=12&q=<quote, URL-encoded>&sig=<base64url>

  • doc is the content hash in the index. A ref dies with its tab. A path must not leave these tools, and a link goes into chat transcripts.
  • q holds the whole quote, never a shortened one, because a shortened quote can match an earlier occurrence (finding R13).
  • The whole link holds at most 4096 characters, the same limit that the link rule uses. A longer link gives link: null and linkUnavailable: "quote_too_long".
  • sig is an HMAC-SHA256 over the text v1\n<doc>\n<page>\n<q>. The signature binds the page and the quote, so nobody can edit a link to point somewhere else.
  • The key is 32 random bytes in <data dir>/agent-link.key, mode 0600, made with wx on first use. The MCP server, the command and the desktop read the same file.
  • The desktop compares signatures with timingSafeEqual.
  • MarkPDF makes a link only for an indexed document. Otherwise the reply carries link: null and linkUnavailable: "not_indexed", with the remedy "Prepare the document first."

Cold start arbitration (finding R5)

When MarkPDF starts only because of a link, it decides about the link before it creates any window. An invalid link, or a valid link that MarkPDF cannot honor, ends the process without a window. A valid link that MarkPDF can honor opens one window with the document.

Security rules for the link

  • A link inside a document never triggers a reveal. A comment beside both scheme lists says why markpdf: must never join them. Through shell.openExternal, the operating system would route the link back to MarkPDF.
  • A link never opens a file outside the read grants. The desktop checks the grant at click time, not when the link was made.
  • A link carries no write action and no text that MarkPDF shows as its own. The quote is only a search key.
  • The label shows "Shown by AI agent" without a name, because the link does not carry one.
  • The handler accepts only the host reveal. Unknown parameters, a repeated parameter, another host, a wrong version or a bad signature end the handling.
  • When MarkPDF already runs, an invalid link changes nothing. The front window shows "MarkPDF ignored a link that it did not make."
  • If the file now has another hash, the reveal still runs. The label says "This document changed after the link was made." not built yet
  • If the index has no such document, or the grant is missing, the desktop opens nothing. A running app shows a notice with the reason.

Registration

On macOS, package.json build.mac gets a protocols entry for the scheme markpdf. The Info.plist then registers the scheme at install. Windows and Linux are out of scope.

Unverified: some agent clients make only http: and https: addresses clickable. The plain citation (document, page, quote) stays in the reply as the fallback.

Every new tool only reads, needs a read grant, and cannot add a grant

No new tool has a write rule. The person's save is the only write. Every reveal in mode show and every suggestion needs a current read grant on the document's file, as default decision 7 confirms. Mode link reads no file and needs only the index.

Why reveal and suggestions need a read grant (finding R2)

This rule is stricter than the index-first rule of read_open_document, on purpose. Reveal matches the quote against the live document in the window. That document can differ from the indexed snapshot that the agent is allowed to read.

Without the rule, the answer shown or page_only, and occurrences, tell an agent about text that it cannot read. read_comments needs the grant also for an indexed document, because the index holds no annotations.

Why no tool can widen its own access (finding R6)

  • The MCP server has no grant operation.
  • The three new commands call requireAccess from core directly. They never use the prompting path in cli/context.ts, also at a terminal.
  • A grant flag (--allow-read, --allow-write, --revoke-read, --revoke-write) with one of these commands is a usage error: "Grant access as a separate command first." The run changes nothing in the consent record.
  • The desktop checks every request again with readAllowlist and requireAccess, because any process of the same user can write a request file.

A person can still run markpdf --allow-read <dir> alone. An agent with a shell can run that command too. That is the existing out-of-band consent model, and this plan does not change it.

Question 3 · where proposals live

A suggestion lives only in the window's memory, in its own tab field

A suggestion is not an overlay. It goes into a new tab field, PdfTab.suggestions. The save and the undo history work on overlays only. Thus no code path can save a pending suggestion, and undo cannot bring back a rejected one.

  • Existing field overlays. exportPdfBytes receives it, the person's save writes it, and the undo history holds it. An accepted suggestion moves here as an owned OverlayItem.
  • New field PdfTab.suggestions. exportPdfBytes never receives it, and the undo history does not hold it. The person cannot edit a pending suggestion. To change the words, the person accepts it and then edits it.

The 2026-09-19 ADR rejected a separate tab field for imported annotations, because they are comments. A suggestion is not an annotation of the document until the person accepts it. A new ADR records this exception.

Outside the window, a suggestion exists only as:

  • The request file in session/desktop-requests/, until the client removes it after the result, or the desktop removes it after one hour.
  • An entry { id, status } in the tab's open-documents record. The entry has no note and no quote.

Status for the agent

The status is pending, accepted, rejected or discarded. accepted records the person's decision only. It does not say that the annotation is still present or saved, and read_comments answers that from the saved file.

The window reports at most 100 statuses for each PDF tab, newest first. list_open_documents adds pendingSuggestions as a count. The field is optional, so the record version stays 2.

Question 3 · how long proposals live

Suggestions live until the person decides, the pages change, or the tab closes after a question

There is no time limit. A cap of 50 pending suggestions in one tab bounds the memory.

Each tab gets a documentRevision counter (finding R3). It increases when the bytes change their page structure: a page insert, delete or move, and an undo or redo that restores other bytes. A suggestion records the revision that it was anchored against.

When the revision changes, every pending suggestion is discarded, and a toast says how many. This rule never leaves a suggestion on the wrong page. A save does not change the revision.

Accept and reject

  • Accept turns the suggestion into an owned OverlayItem with origin: { kind: "agent", agent, suggestedAt, acceptedAt }. It uses the normal edit path: one history entry and dirty: true. The person can undo it, and a running preparation stops.
  • Reject removes the suggestion. It changes no overlay, adds no history entry and does not set dirty.
  • A new suggestion updates the tab as an automatic change without dirty, so it does not count as a user edit.
  • After acceptance, the annotation belongs to the person, who can edit, move or delete it.

Encoding (finding R1)

The agent annotation writes /T and /Contents with PDFHexString.fromText, which encodes UTF-16 and needs no escaping. Thus parentheses, backslashes, non-Latin names, emoji and text that looks like PDF syntax stay literal text.

The person path keeps PDFString.of in this iteration, because a change there is outside the scope. The plan reports that latent escaping risk on the person path to the user.

The agent name

The name comes from the MCP initialize handshake, clientInfo.name, which the SDK exposes with getClientVersion(). The command line takes --agent <name> and defaults to "markpdf command line". The built markpdf reveal also takes --agent, for the label.

The name is a label that the client reports about itself. It is not an authenticated identity (finding R1). The desktop removes control and bidirectional-override characters and cuts the name to 64 characters.

Flattened saves · finding R11 · default decision 8

A flattened copy cannot keep the agent name, so MarkPDF asks first

A flattened save or export writes no metadata and no standard annotations, and it paints comments without an author. When the tab has accepted agent annotations, MarkPDF asks: "This copy will not record that an AI agent wrote 2 of its annotations. Save it anyway?"

Agent marks keep the violet colour in the flattened copy, as the only remaining visible sign.

After a reload of the saved file in MarkPDF, the keyword gives back the agent origin. Thus the page and the pane look the same as before the save. parsePersistedOverlays drops an invalid origin but keeps the overlay.

Unverified: the exact display in Acrobat and Preview. Capability 5 records a manual check with screenshots, and that check is verification, not Red evidence.

Question 7 · output bounds

One core reply builder bounds read_comments for the command line and for MCP

The bounds live in core, and both surfaces use them (finding R10). Before this plan, the command line applied no output bound.

  • core/annotations/commentsReply.ts builds the read_comments reply. It cuts each note and quote at 4000 bytes and gathers items with boundItems under DEFAULT_CONTENT_BUDGET.
  • It fits the reply with fitReply under DEFAULT_REPLY_BUDGET. The reply reports truncated, totalComments, nextOffset and omittedBytes.
  • markpdf comments prints that reply, as JSON or as text, and never more than the reply bound.
  • reveal and suggest_annotation return fixed fields and a link of at most 4096 characters, through fitReply. The server's final check applies to all three tools. deviation The built runners do not call fitReply, because their replies are fixed-size by construction.
  • Refusal messages go through boundText after safeForTerminal, as all refusals do.
  • The desktop result file has a 16 KiB limit on the opened descriptor and a field-by-field parser, like parsePreparationReply.

Pagination (finding R9)

Items come in page order, then top to bottom, then left to right, as the pane lists them. offset is the index of the first item to return. The reply carries documentHash, the SHA-256 of the saved file, and nextOffset or null.

When documentHash changes between two calls, the file changed, and the agent starts again at offset 0. Each item is smaller than the content budget, because of the 4000-byte cut. Thus every call returns at least one item, and pagination always moves forward.
